# Rollout, effort and acceptance budgets

No citywide implementation authorized by this research deliverable. Estimates are engineering work **after prerequisites arrive**, for one engineer familiar with the repository; source/owner response time is unbounded and excluded. Suggested order is **routing checkpoint → Phase0 → A → bounded B/D slices → C → E**, with source acquisition in parallel. C can move earlier once authoritative trail/canopy data are ready. Seasonal decoration is last and separately selectable.

## Proposed acceptance gates

These are **new targets**, not demonstrated results. A slice must pass repeated paired measurements against the immediately preceding accepted state and cumulative comparison to Step6.1. Keep identical camera/date/time/traffic/view/DPR/browser conditions. Run browsers serially; retain three alternating rounds and all raw data, including outliers/initial failures.

| Gate | High-end reference target | Constrained hardware target |
|---|---|---|
| Hardware definition | Same5070Ti/Edge setup as baseline, plus whole-city overview | Select and record an actual integrated/mobile GPU, CPU, RAM, resolution/DPR and browser before claiming support; initial prototype1280×720,DPR1 |
| Map-ready | Each bounded slice median increase **≤100ms**; cumulative **≤250ms** over paired freshStep6.1 reproduction | First establish device baseline; proposed delta **≤250ms/slice**, cumulative **≤500ms**; absolute target **≤8s** subject to measured feasibility |
| Frame intervals | Paired p95 increase **≤1ms/slice**, cumulative **≤2ms**, absolute p95 **≤16.7ms** in all acceptance views | Proposed absolute p95 **≤33.3ms**, p95increase **≤3ms/slice**; if base scene already fails, optimize base geometry/LOD before accepting extra lights |
| Daytime | p95increment **≤0.5ms/slice**; no night-only page rebuild/upload in steady day; no new time-toggle shader programs | Same correctness gate; measure actual cost, do not assume shader branch removes allocation/CPU work |
| Geometry/calls | Incremental visible triangles **≤100k/slice** and calls **≤40** per fixed local view; cumulative lighting-related triangles≤250k/calls≤100; separate forest geometry slice gate | Proposed near/far fixture LOD; incremental≤50k visible triangles/≤25calls per slice, contingent on measured baseline |
| Heap/buffers | Post-GC JS heap increment **≤10MB/slice**, cumulative≤20MB; lighting CPU+GPU buffer byte estimates **≤16MB cumulative** excluding forest | Initial lighting byte target≤8MB, post-GCheap delta≤10MB cumulative; verify driver behavior separately |
| Forest allocation | Separate prototype budget: ≤32MB resident geometry/instance estimates and≤200k extra visible triangles, then measure overdraw/frame time | Initial≤16MB/≤100k extra visible triangles; tune density/LOD without filling protected clearings or falsifying observed canopy |
| Shader cost | No extra variants on toggles; paired startup compile/link wait increase≤100ms where reliably instrumented; otherwise report unavailable and use startup/program gates | Must sample actual device; limit variants and require stable program count |
| Capacity/lifecycle | Zero **unapproved** cell overflows; device texture limits enforced; no leaks across10 load/dispose cycles and context restore | Same correctness gate; no silent source loss or failed restoration to reduce RAM |

Triangle/call/memory maxima are independent ceilings, not permission to spend all simultaneously. If baseline itself fails absolute frame/memory targets, classify that device/config unsupported pending scene optimization. Never advertise constrained hardware acceptance from desktop arithmetic. Retain daytime pole geometry where visible; only inactive nighttime resources are candidates for lazy loading.

Overall work is several separate implementation/review tasks and likely multiple weeks; summing these exploratory ranges into a fixed citywide deadline would hide source/geometry unknowns. Data licensing/current fixture availability, existing large static-buffer cost, transparency/vegetation and shader compilation are the main schedule/performance risks. Stop each phase at its definition of done and re-baseline only after acceptance.
